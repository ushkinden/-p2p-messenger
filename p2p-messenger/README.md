# Прямая связь — P2P-мессенджер без сервера сообщений

Переписка идёт напрямую между двумя устройствами (WebRTC), сообщения нигде
не хранятся, кроме самих устройств. Тексты, фото, видео и файлы. Если
получатель офлайн — сообщение остаётся у отправителя и уходит само, как
только получатель появится в сети.

Проект состоит из двух независимых частей:

```
p2p-messenger/
  signaling-server/   — крошечный сервер-«справочная» (Node.js)
  client/              — сам мессенджер: статичные HTML/CSS/JS, без сборки
```

## Как это устроено и что действительно происходит без сервера

**Сигнальный сервер НЕ хранит и не читает сообщения.** Его единственная
задача — знать, какие номера сейчас онлайн, и передать двум устройствам
служебные технические данные (адреса и параметры соединения), чтобы они
смогли открыть прямой канал друг с другом. Как только канал открыт,
сервер в переписке больше не участвует — текст, фото, видео и файлы идут
напрямую, «из рук в руки».

Это принципиально отличается от обычного мессенджера (как я делал в
прошлый раз): там сервер — часть системы постоянно, здесь — только
временный посредник для знакомства двух устройств.

**Важное следствие**, о котором мы договорились: раз сообщения нигде не
хранятся кроме устройств — если отправитель напишет, закроет вкладку/
приложение, а получатель так и не выйдет в сеть, сообщение просто останется
лежать у отправителя и уйдёт, когда он **сам** снова откроет приложение
(с интернетом) и получатель окажется в сети. Это не «мессенджер с историей
на сервере» — это осознанный компромисс, о котором ты просил.

## Почему всё же нужен сигнальный сервер (и когда — ещё и TURN)

Два устройства в разных сетях почти никогда не видят друг друга напрямую
из-за NAT (трансляции адресов у роутеров). Чтобы просто «найтись» —
нужен посредник. Это и есть сигнальный сервер из этого проекта — лёгкий,
без базы данных, без переписки внутри.

Дальше, чтобы **установить сам канал**, обычно достаточно бесплатных
публичных STUN-серверов Google (уже прописаны в клиенте по умолчанию).
Но примерно в 10–20% случаев (строгий NAT, некоторые мобильные операторы,
корпоративные сети) без **TURN-сервера** соединение не пробьётся — тогда
нужен сервер-ретранслятор, который просто перегоняет уже зашифрованный
трафик, не читая его. Полноценный TURN (обычно ПО `coturn`) сложнее лёгкого
сигнального сервера — ему нужны открытые UDP-порты, чего не даёт
большинство бесплатных Node.js-хостингов (Render/Railway и т.п. — только
HTTP/WebSocket). Варианты:

1. Для начала — просто попробовать без TURN (STUN часто и так работает,
   особенно в домашних сетях).
2. Если не соединяется — использовать бесплатный сторонний TURN, например
   [Open Relay Project от Metered.ca](https://www.metered.ca/tools/openrelay/)
   (даёт бесплатные `turn:` данные) или похожий сервис — просто вписать
   выданные адрес/логин/пароль в настройки клиента (там есть поля).
3. Или поднять свой `coturn` на VPS с реальным IP — это уже не «пара
   кликов», в отличие от сигнального сервера.

## 1. Сигнальный сервер — запуск и деплой

```bash
cd signaling-server
npm install
npm start
```

Поднимется на `http://localhost:4000` (задаётся через переменную `PORT`).
Проверка: `curl http://localhost:4000/health` → `{"ok":true,"online":0}`.

**Чтобы им могли пользоваться два человека в разных местах**, задеплойте
его так же, как мы делали для прошлого мессенджера — Render.com или
Railway.app, бесплатный Web Service, Build Command `npm install`, Start
Command `npm start`. После деплоя у вас будет адрес вида
`https://ваш-сервис.onrender.com` — для клиента его нужно указать как
`wss://ваш-сервис.onrender.com` (именно `wss`, не `https`).

## 2. Клиент — запуск и деплой

Это обычный статический сайт (HTML/CSS/JS, без сборки), но браузеры не
разрешают WebRTC и буфер обмена на страницах, открытых просто как файл
(`file://`) или без HTTPS — нужен хотя бы простой веб-сервер.

**Проверить локально:**

```bash
cd client
npx serve .
# или: python3 -m http.server 8080
```

Откройте адрес, который покажет команда (например, `http://localhost:3000`
или `http://localhost:8080`).

**Чтобы пользоваться через интернет** — задеплойте папку `client/` на
любой бесплатный статический хостинг с HTTPS "из коробки": GitHub Pages,
Netlify, Vercel или Cloudflare Pages. Файлы никак не собираются — просто
загрузить содержимое папки `client/` как есть.

## Как начать переписку

1. Задеплойте `signaling-server`, получите его `wss://...` адрес.
2. На каждом устройстве откройте клиент, при первом запуске укажите имя
   (только для себя) и адрес сигнального сервера (`wss://...`).
   Устройству автоматически присвоится случайный **9-значный номер**.
3. Обменяйтесь номерами с собеседником любым удобным способом (лично,
   сообщением в другом мессенджере и т.п. — это не публичный каталог).
4. Каждый добавляет номер другого через «+ Добавить» в списке контактов.
5. Как только оба онлайн — можно писать, слать фото/видео/файлы. Если
   собеседник офлайн — сообщение уйдёт автоматически, когда он появится.

**Почему нужно добавить друг друга контактом заранее:** клиент принимает
входящее соединение только от номеров, которые уже есть в списке
контактов — иначе кто угодно, перебирая номера, мог бы пытаться
достучаться. Само пространство номеров большое (миллиард комбинаций), но
это не заменяет обычную осторожность.

## Известные ограничения (честно, чтобы не было сюрпризов)

- **Работает, пока открыто приложение.** Здесь нет push-уведомлений
  (как в обычных телефонных мессенджерах) — чтобы получить сообщение,
  вкладка/приложение должно быть открыто и в сети. Для полноценной работы
  в фоне на телефоне это отдельная, более сложная задача (нужны
  Android/iOS push-сервисы Google/Apple — тоже, по сути, сервер).
- **Хранилище — только на устройстве** (IndexedDB в браузере). Если
  очистить данные браузера — переписка на этом устройстве потеряется.
  Между устройствами история не синхронизируется (у каждого — своя копия).
- **Большие видео передаются медленно**, особенно без прямого соединения
  (через TURN-релей). Лимит на файл в коде не выставлен искусственно, но
  практически стоит ориентироваться на разумные размеры (до сотен МБ).
- **Нет отметки "прочитано"** и индикатора набора текста — оставил только
  базовые статусы (ожидает / отправлено).

## Дальше на Windows, Android, iOS

Сама модель (сигнальный сервер + WebRTC p2p-канал) переносится один в
один. Меняется только «обёртка»:

- **Windows** — можно почти без изменений: обернуть этот же HTML/CSS/JS
  через **Tauri** или **Electron** в нативное приложение — либо взять
  готовый веб-код как есть внутри WebView.
- **Android / iOS** — тоже возможно (WebRTC поддерживается нативно на
  обеих платформах), но там появляется отдельная задача: чтобы сообщение
  доходило, когда приложение свёрнуто, обычно используют push-уведомления
  через Google Firebase Cloud Messaging / Apple Push Notification service
  — это будет отдельный шаг, когда дойдём до мобильной версии.

Когда решишь двигаться дальше — скажи, с чего начать (Windows-обёртка или
сразу мобильные), и продолжим.
